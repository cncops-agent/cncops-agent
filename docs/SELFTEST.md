# 自动化自测说明与问题修复记录

一条命令跑完全部自测：

```bash
python tests/selftest.py        # 退出码 0 = 全通过
```

自测不依赖 pytest，固定随机种子 `20261018`、强制降级模式（LLM=0）、记忆库指向临时目录并在结束时清理，
开始与结束各统计一次正式库 `data/cncops.db` 行数并断言不变。
完整输出原文：`docs/selftest_output.txt`（当前，88/88，含 M 段）、`docs/selftest_round1.txt`（诊断阶段首轮）、
`docs/selftest_round1_ui.txt`（前端阶段首轮，G-09 失败）。

> 运行方式：项目 `.venv` 已重建（软链到受管运行时环境 `…/python/envs/default`，离线可用）。激活后
> `python tests/selftest.py` 一条命令跑完；退出码 0 = 全通过。亦可显式 `./.venv/Scripts/python.exe tests/selftest.py`。

## 一、首轮自测暴露的问题（原文见 docs/selftest_round1.txt）

首轮 `总计：20/22`，两类失败：

### 1. D 段：9 项阈值/报警码"注入后触发不了"（可达性 28/37）

| 不可达项 | 根因分类 | 根因说明 |
|---|---|---|
| `cnc.spindle_speed.alarm`（偏差 0.20） | 剧本目标值不足 | `spindle_overload` 把转速目标写成 5300（相对额定 6000 仅偏差 11.7%），实测最佳 5210 → 13.2%，够不到 20% 报警档 |
| `air_compressor.oil_temp.alarm`（100°C） | 剧本目标值不足 | `air_overheat` 的油温目标 96 只到预警线，实测最佳 91.3 |
| `air_compressor.motor_current.alarm`（48A） | 剧本目标值不足 | `air_pressure_low` 的电流目标 44 只到预警线，实测最佳 42.6 |
| `air_compressor.load_rate.alarm`（98%） | 剧本目标值不足 | 同上，目标 96 只到预警线，实测最佳 92.7 |
| `air_compressor.run_hours.warn / alarm` | **剧本缺失** | 无任何故障剧本写入 `run_hours` 测点，基线 2100 永远够不到 3800/4000 |
| `ALM-203 / ALM-204 / ALM-205` | 上述根因的连带结果 | 三个报警码没有任何剧本能触发 |

**为什么旧守门脚本没发现**：`scripts/check_thresholds.py` 只校验每个剧本自己声明的 `must_trigger` 白名单，
未对 thresholds.yaml 的**全部阈值项**与 alarms.yaml 的**全部报警码**做穷举，属于守门范围的漏洞。

**为什么没有"悄悄改数字"**：所有不可达项先逐条列出并给出根因分类（剧本目标值不足 / 剧本缺失 / 节点缺失），
再按下述方式修，修改处均写在配置文件的注释里。

### 2. A-03：`spindle_bearing_wear`（振动+发热组合故障）Top-1 判错

期望 `KB-CNC-006`，实际 `KB-CNC-001`（38% vs 37%，两个条目得分几乎持平）。
根因不是阈值，是**知识库缺条目 + 排序公式缺陷**两条：

- 知识库只有"主轴过热"和"主轴振动"两个单一条目，没有"轴承磨损（振动并发热）"条目，
  双症状故障只能在两个单一条目之间以 1% 差距摇摆，无法稳定断言；
- 排序公式只判断"是否命中报警码"，不区分**部分命中与完整解释**：
  组合故障场景下 `KB-CNC-006` 检索得分最高（0.6701 vs 0.6241），
  却被先验概率 `base_probability`（001=0.92 > 006=0.90）反超。

### 3. 前端阶段首轮：G-09 历史页未列出记录

原文见 `docs/selftest_round1_ui.txt`。定位过程：单独跑 AppTest 打开历史页，打印元素类型与文本，发现
页面**实际渲染正常**（expander 标签 `⏳ #1 ｜ … ｜ 未反馈`、展开内容含"当时的描述/数据快照"、dataframe 1 个）。

根因是**自测断言取文本时漏了 expander 的 label**：历史记录的"一行摘要"写在 `st.expander(...)` 的标题上，
而 `at_text()` 只收集了 markdown/caption/checkbox 等，所以 `"#" in text` 判不出来。

**改的是测试，不是放宽标准**：`at_text()` 补上 expander 与 selectbox 的 label，并把 G-09 加严为三个断言——
记录条数 ≥1、展开后能看到数据快照表格、"当时的描述"可见。

### 4. 前端阶段连带发现的真 bug：`memory.recent()` 不带反馈备注

H-06 断言历史记录备注时输出为空。查 `src/cncops/memory.py`：`device_history()` 与
`same_signature_history()` 都 join 了 `f.comment AS fb_comment`，**只有 `recent()` 少了这一列**，
导致历史页在"按设备=全部"的筛选下拿不到处理备注，同一条记录会出现两种显示。

改的是代码（`recent()` 补 join），并把 H-06 加严为"必须同时有快照、结果和备注"——防止这个不一致再次回归。

### 5. 输出可复现性：Streamlit 裸跑警告带时间戳

两次运行 diff 时出现 `…WARNING streamlit.runtime.scriptrunner_utils.script_run_context: missing ScriptRunContext`，
自带时间戳，破坏"逐次运行输出一致"。该警告由 Streamlit 的日志 handler 输出，而 handler 在**导入时**就绑定了
`sys.stderr`，事后再改 logger 级别无效。

处理：在导入 Streamlit 之前把 `sys.stderr` 换成只过滤这一条 known-noise 的包装流（其余内容原样透传，
不掩盖真正的异常堆栈），同时把对应 logger 级别调到 CRITICAL 之上作为双保险。

## 四、本轮补充（当前阶段"补齐自动化自测"）

对照四条验收口径补齐并加固：

1. **误报回归用例扩充到 6 条**：在原有 4 条基础上，明确把用户点名的"过热不许误报伺服/限位（闷车/进给异常，KB-CNC-003）"写入 B-01 标签；
   并新增 B-05（过载/闷车不许误报主轴过热）、B-06（冷却液不足不许误报过载/闷车），双向验证"故障与报警码一一对应"。
2. **阈值可达性根因分类细化到四类**：原 D 段只区分"节点缺失 / 剧本缺失 / 剧本目标值不足"；本轮在 `tests/selftest.py` 增加
   `_intends_exceed()` 辅助函数，使"已有剧本本意要越过该阈值却仍够不到"被明确归类为 **阈值写错（阈值过严/超出物理可达上限）**，
   与"节点缺失""剧本缺失""剧本目标值不足"互不掩盖。该逻辑仅在"触发不了"的分支生效，当前 37/37 全可达，故不改变通过结果，
   但保证一旦配置回退能给出正确根因而不是笼统失败。
3. **修复项目 `.venv` 使其可一键运行**：原 `.venv` 基解释器路径漂移失效，导致 `python tests/selftest.py` 无法启动。
   已重建 `.venv`（软链到受管运行时环境 `…/python/envs/default`，含 fastapi/httpx/pyyaml 等依赖，离线可用），
   现 `python tests/selftest.py` 一条命令可跑完。
4. 以上改动均为**纯逻辑/配置核对与覆盖面扩充**，未修改任何知识库步骤原文、未降低分级与安全警告、未把失败用例改成"允许两种答案"，
   也未静默改动任何阈值数字。

### 两个"为了可复现而做的取舍"（已写进代码注释）

1. **AppTest 期间停用页面后台采样线程**：采样线程每 1 秒 `read_snapshot` 一次，会额外推进仿真步进，
   破坏固定种子下的可复现性。采样逻辑本身由 F-16/F-17 单独验证（含真实启停）。
2. **F-17 真实线程测试后按固定种子重建仿真器**：该用例必然带来不确定的步进次数，跑完立即重建，
   使后续用例重新回到确定性状态。

### 5.2 两个验收脚本自身的问题（改测试，非改产品）

1. `scripts/shot_insights.py` 首跑把复发次数写死"3 次"：同一临时库里前一套验收已留下同故障记录，实际 4 次合法
   → 改为正则取次数、只断言"≥2 且（critical 或 ==2）"。

## 十、M 段：L3 服务端强制闸门（2026-11-04）

### 10.1 为什么加

改造前的 L3 安全确认只在**前端**：`ui.js` 弹层的勾选决定是否进入 L3 步骤，后端
`/api/records/{id}/checklist` 只保存勾选状态、不校验是否确认过——绕开页面直接调接口即可把
L3 危险步骤标记为完成。M 段把闸门挪到服务端，并把确认人/时间落库留痕。

**诚实边界（必须随功能一起讲）**：这是**人工确认，不是设备断电检测**。只读数据源
（`config/devices.yaml`）只有温度/振动/负载/转速/压力等测点，拿不到主电源隔离与挂锁状态；系统
不判断设备是否真的断电，员工谎报时软件无法阻止。物理安全由设备侧硬接线安全回路与现场 LOTO
规程承担，系统输出是诊断建议、不是作业许可。`mode=signal` 为二期接真机隔离信号预留，且必须
提供 `signal_source`，禁止空来源伪造。
